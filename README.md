## 原著有据可查，本作设定由你决定。

写同人最麻烦的，往往不是想剧情，而是记住原著到底写过什么，以及这一版你到底改了什么。

「同人工作室」把这两件事分开：

- **原著 Canon**：每条事实都带章节、偏移和原文引文，由作者逐条确认；
- **本作设定（Fic Canon）**：你故意改掉的关系、时间线、知情、世界规则和称呼，单独记账。

写之前，场景契约把两者一起交给 AI，**【本作】永远在最前面**；写完之后，检查器只指「在哪、凭什么、跟哪条设定冲突」，不逼你改回原著。

**默认关闭** · **不写正文** · **不替你改稿**

```text
导入原著 → 确认 canon → 声明本作设定 → 写一张章节任务卡 → 编译场景契约 → 在工作区写 → 检查 → 登记改动
```

## v0.2.1 修复：0.2.0 会让 DSH 的所有对话返回 400

**如果你装过 0.2.0 并执行过 `/fic on`，请升级到 0.2.1 并重启 DSH。** 0.2.0 里六个 `fic_*` 工具把内部参数表直接当
JSON Schema 交给了宿主，而新增的 `fic_plan` 有个参数叫 `title`——它正好是 JSON Schema 的注解关键字。后果是开启同人工具后
每条消息都失败（`Invalid schema for function 'fic_plan': … is not of type "string"`），而且 `/fic on` 会被记住，
重启后**每个新会话**都中招，与是否在写同人无关。

临时自救：在会话里 `/fic off`，然后**重启 DSH**（`/fic off` 只对当前进程生效）。升级到 0.2.1 则不需要这一步。

## 这个版本（v0.2.1，功能面同 0.2.0）

- **只读服务 `novelFanfic`**：`identity / getStatus / getRevision / getContract / getCanonSummary / onDidChange`。
  别的插件（故事总控）能按能力读到「这一章的契约是哪一版」，不用猜。服务只读、永不读夹具。
- **项目版本号**：`project.json.revision`，任意一次写操作 +1（确认提案 / 本作改动 / 私设 / 忽略 / 导入 / 任务卡）。
  面板右上角那个 `v17` 就是它。
- **章节任务卡**：写之前 5 分钟想清楚「这一章要干什么」。一句话目标 + 情绪曲线 + 最多 7 个节拍 + 开放问题；
  可编辑、可丢弃，不是契约、不进 canon。唯一进契约的地方是「开放问题」→「不确定」段。
- **面板重做**：4 个入口（原著 / 本作 / 剧情 / 写作）+ 顶部一行「下一步」；右下浮动按钮删掉；
  审阅收进顶栏「待办 N」。
- **检查和忽略的口径统一**：作者忽略过的 finding 在服务端就被应用，`fic_check` 的 `pass` 与面板看到的一致。

完整改动见 [CHANGELOG.md](CHANGELOG.md)，服务契约见 [docs/contract.md](docs/contract.md)。

## 快速开始

不用改变原来的写作方式，也不用一直开着。

### 1. 安装

```bash
dsh plugin --profile web add dsh-novel-fanfic
```

或直接从 GitHub 安装：

```bash
dsh plugin --profile web add github:DrizzleGig/dsh-novel-fanfic
```

装好后重启 Harness。需要 Node.js ≥ 20，插件本身零依赖。

### 2. 开启

默认关闭。在要处理原著的会话里：

```text
/fic on
```

开启后，`fic_analyze` / `fic_avatar` / `fic_check` / `fic_contract` / `fic_lookup` / `fic_plan` / `fic_source` / `fic_state` 八个工具才进入模型工具表；关掉用 `/fic off`。

### 3. 导入原著

面板里点「导入原著」，或：

```text
/fic import D:/books/原著.txt
```

v0.1 只支持 TXT / Markdown（UTF-8 或 GB18030，≤20 MB）。导入后自动分章、建索引；canon 提案默认是 `pending`，作者确认后才进入契约。

### 4. 声明你要改什么

在面板「设定 → 本作」里写本作前提和改动，或：

```text
/fic delta add --kind relationship --title "裴照与沈砚是恋人" --text "本作中两人自 ch002 起是恋人；原著里的上下级关系不再适用。" --subjects 裴照,沈砚 --from ch002
```

本作设定会写进契约的【本作】段，并优先于原著。

### 5. 在会话里写，不在侧边栏写

打开右下角「写作准备」：

1. 选章节；
2. 点「去会话开写」——起稿指令会复制到剪贴板；
3. 到工作区新建一个对话，粘贴后让 AI 按这一章写；
4. 写完把草稿贴回「写作准备」，运行检查。

侧边栏只做资料台、契约和检查；正文永远在工作区的会话里。

### 6. 看检查结果，决定怎么处理

每条 finding 都带「在哪、凭什么、跟哪条设定冲突」。你可以：

- **看原文**：跳到那一章并高亮引文；
- **登记为改动**：这不是错，是我故意的——写一句说明，它就成为本作设定，以后同类不再按原著报；
- **忽略**：只放过这一次，必须写理由，落在 `waivers.json`，可撤销；
- **改稿**：检查器不自动改，改不改由你。

## 它解决什么

| 常见问题 | 同人工作室怎么处理 |
|---|---|
| 记不住原著细节 | 导入后生成可核 canon，每条事实带章节 / 偏移 / 引文；`fic_lookup` 按问题查原文 |
| 写着写着接不上 | 场景契约固定视角、在场、称呼、知情、世界规则、时间线、禁忌、未定项、锚点 |
| 二创改动被当成错误 | 本作设定（Fic Canon）优先于原著；检查器按它放过同类 finding |
| 写完不知道哪里错 | 12 项确定性检查；每条 finding 说清「在哪、凭什么、跟哪条设定冲突」 |
| 改一次报一次 | 「登记为改动」是持久的；「忽略」只对这一次 |

## 本作设定：不干涉二创

这是 v0.1.0 最重要的机制。权威顺序是：

```text
作者当场指令 > 本作设定（Fic Canon） > 原著 canon > 未定（自由）
```

- **契约**：有本作设定时，【本作】放在九段契约最前面，并写明「本作设定优先于以下原著事实；冲突时按本作写」。
- **检查器**：作者登记过的差异，会按 `suppress` 指纹放过同类 finding，并在 `suppressed` 里显示「按哪条本作设定放过」。这不是静音——放过了什么、为什么放过，都能看见。
- **两种「不报」要分开**：
  - **本作设定**：持久的设定，会影响后续契约；
  - **忽略（waive）**：一次性的，只对当前这条 finding 有效。

作者私设（AU / 私设句 / 错名）是另一套：它是「检查器要抓的签名」，用来发现原著向场景里混进了 AU；本作设定是「本作正式生效的设定」。两者不混。

## 一个真实的写作场景

假设你在写一部长篇同人：原著里，某个秘密到后期才揭晓；你想让主角提前知道。

1. **原著有据**：导入原著，确认相关事实。canon 记下这个秘密在哪一章揭晓，带偏移和引文。
2. **声明本作改动**：在「本作」里写：「主角在第二章结束时已经知道这个秘密；此后不得写成第一次听说。」
3. **生成契约**：下一章的【本作】段写「主角已知情」；知情段写清谁知道、谁不知道。
4. **写作**：AI 在工作区按契约写。主角可以知道，但不能无依据地推断别人也知道。
5. **检查**：如果草稿写「主角第一次听说」，检查器报 `knowledge`；如果这是你故意让他装作不知道，点「登记为改动」，写清「他在套话，不是不知道」。
6. **下一章**：契约里仍然有这条本作设定，检查器不再把它当原著错误。

**决定由你下，AI 负责把设定记住。**

## 怎么用

你大概会这样说：

| 你说的话 | 它会做什么 |
|---|---|
| 这个人第几章出场？他属于哪个势力？ | 人物卡 + 关系 + 原文证据 |
| 这一章谁在场？谁知道什么？该怎么称呼？ | 编译这一章的场景契约 |
| 我这里把时间线提前了，可以吗？ | 记进本作设定，契约按本作写 |
| 这段是不是写错了？ | 跑 12 项检查，每条带位置、依据、冲突设定 |
| 这是我故意的，别再报了。 | 登记为本作改动，同类 finding 以后放过 |
| 下一章别忘了这个改动。 | 本作设定一直留在契约里 |

## 它不做什么

| 它不做什么 | 实际职责 |
|---|---|
| 不写正文 | 正文在工作区会话里创作 |
| 不自动改稿 | 只给 finding，改不改由作者决定 |
| 不给作品打分 | 不评判文笔、剧情或文学水平 |
| 不强制遵守原著 | 本作设定可以明确覆盖原著 |
| 不替作者决定剧情 | 作者保留所有改编决定权 |
| 不保证发现所有错误 | 检查器是确定性规则 + 启发式，用于辅助核对 |
| 不做语义向量检索 | `fic_lookup` 是词面检索，不是 RAG |
| 不支持 PDF / EPUB | v0.1 只支持 TXT / Markdown |
| 不联网、不爬取 | 插件只读写本地项目目录 |

## FAQ

### Q1：为什么默认关闭？

同人工作室会读原著、建 canon、编译契约，不是每个会话都需要。默认关闭，`/fic on` 只对当前会话生效；关掉后工具从模型工具表移除，不占上下文。

### Q2：我改了原著，检查器会不会一直报错？

不会。把改动写进「本作」，契约就会按本作写；如果希望检查器不再按原著报同类问题，在具体 finding 上点「登记为改动」——它会把这条差异连同 `suppress` 指纹一起落进本作。检查器的目标是找「跟设定冲突」，不是找「跟原著不一样」。

### Q3：Canon 是 AI 自动生成的吗？

原著事实由导入内容和模型提案生成，但每条都要作者确认。每条记录保留章节、偏移和引文，作者可以回到原文核对。未经确认的提案不进入契约。

### Q4：检查器会直接改我的正文吗？

不会。只返回 findings：位置、依据、冲突设定、建议；改不改、怎么改，由作者决定。也不评分。

### Q5：支持 PDF / EPUB 吗？

v0.1 不支持。TXT / Markdown 之外的格式需要先转换。EPUB / PDF 在 v0.2 的路线里。

### Q6：`fic_lookup` 是语义检索吗？

不是。v0.1 是词面检索（实体命中 + 问题词 + 整句匹配），不是向量 RAG。它能回答「这句话原文在哪」，但不做语义召回。

### Q7：数据保存在哪里？

`.dsh-novel-fanfic/<project>/`，包括 `source/`、`canon/`、`deltas.json`、`declarations.json`、`waivers.json`、`audit.jsonl`。不同项目分开管理；插件关闭不会删除数据。

### Q8：会和 fade / beat 冲突吗？

同人工作室是独立插件，不依赖其他写作插件。它的账本是「原著事实 + 本作设定」，不写 fade 的记忆账本，也不写 beat 的剧情决策账本；同时装多个插件时，注意工具名和文件边界即可。

### Q9：为什么叫 Fic Canon？

Canon 是原著事实；Fic Canon 是「这一版同人正式生效的设定」。把两者分开，才能既沿用原著，又不被原著绑死。

### 设计原则

1. **原著事实必须可追溯**：没有引文的事实不进 canon。
2. **本作设定优先**：作者明确的改编不能被原著覆盖。
3. **场景约束前置**：动笔前说清视角、在场、称呼、知情、世界规则、时间线。
4. **检查结果必须有依据**：每条 finding 都能回答「在哪、凭什么、跟哪条设定冲突」。
5. **作者拥有最终决定权**：不自动改稿，不打分，不替作者决定改编方向。
